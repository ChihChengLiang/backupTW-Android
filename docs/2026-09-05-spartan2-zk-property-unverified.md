# Unverified claim: vendored Spartan2 fork may not be zero-knowledge (2026-09-05)

## Summary

The zkID circuit's actual key-generation/proving backend (reached via
`ecdsa-spartan2`, which `openac-age-mobile-app`'s `setup_jwt_keys` /
`setup_show_keys` call) is **not** Groth16 and does **not** use a
Powers-of-Tau/trusted-setup ceremony — it's a
[Spartan](https://eprint.iacr.org/2019/550) SNARK (Setty, CRYPTO 2020) via a
vendored fork, which is transparent by construction (no toxic waste, no
ceremony). That much is a non-issue.

What *is* an open issue: the vendored fork's own README states, describing
the library in general terms:

> "The proofs are *not* zero-knowledge (we plan to add it in the near
> future)."

This has not been verified as stale-vs-live for the exact branch/commit this
project depends on. If it is accurate for that commit, proofs generated by
this backend could leak witness information (e.g. the hidden birth date) —
which would defeat the entire purpose of the age-predicate circuit. This is
strictly more serious than a trusted-setup concern, since a leaky witness
undermines the privacy property the whole OpenACAge design exists for.

- Fork: [`0xVikasRushi/Spartan2`](https://github.com/0xVikasRushi/Spartan2),
  branch `openac-sdk`.
- Commit actually resolved by Cargo at time of writing:
  `d687dbb` (full hash not captured; re-resolve via `Cargo.lock` in the

- Quoted line is from that commit's top-level `README.md`, in the "About

- Key generation call site: `ecdsa-spartan2/src/setup.rs`,
  `setup_circuit_keys` / `setup_circuit_keys_no_save`, which call
  `R1CSSNARK::<E>::setup(circuit)` directly — no ceremony, no ptau, matches
  the transparent-setup claim. This part of the finding is confirmed, not
  speculative.

## Why this wasn't caught by build-ios.sh / RELEASE-openac-age-v1.md

Neither document asserts anything about the zero-knowledge property of the
underlying SNARK — they track hash/size integrity of the compiled
artifacts (R1CS, proving/verifying keys), not the cryptographic properties
of the proof system itself. A byte-identical, hash-verified key can still
be generated by a scheme that doesn't hide the witness; hash pinning and
ZK-soundness are orthogonal concerns.

## Open follow-up

- Read `0xVikasRushi/Spartan2`'s actual Hyrax/Bulletproofs polynomial
  commitment implementation (not just its README) at the exact commit
  Cargo resolves, to determine whether blinding/hiding is actually
  implemented for the `openac-sdk` branch, or whether the upstream
  README's caveat is live.
- If confirmed non-ZK: this blocks treating any proof from this backend as
  privacy-preserving. The birth-date predicate proof would need a
  ZK-hardened backend before any real (non-test-vector) use — this is a
  cryptography question, not an engineering one, and needs someone with
  Spartan/Hyrax expertise, not just a code read.
- If confirmed a stale README artifact carried over from upstream: still
  worth a one-line note in `OpenACAge/README.md` recording that it was
  checked and found stale, so the next person doesn't have to re-derive
  this.
- Cross-reference: the iOS team's own `upstream-reports.md` already tracks
  one zkID-related upstream issue ("pk_commit 隱藏性只靠證明端保證" — the
  hiding property of `pk_commit` relies only on the prover's own
  guarantee). This finding may be related or may be a separate root cause
  — worth checking both against the same underlying commitment-scheme
  code once it's read.

## Status

Unverified. Functional validation (Phase 1's fixed-vector go/no-go gate,
`age_assets.rs`) was continued in parallel per project-owner direction
2026-09-05, since functional correctness and the ZK property are
orthogonal and the fixed-vector run is cheap to keep exercising — but its
passing does **not** clear this concern, and should not be read as doing
so by anyone reviewing this later.
